## Concurrency Control

Any time more than one query needs to change data at the same time, the problem of concurrency contorl arises.

MySQL has 2 levels:
- Server level
- Storage engine level

The spreadsheet problem.

### Read/Write Locks

Multiple clients read the same file simultaneously, there's nothing wrong.
Someone try to delete a cell number while others are reading the spreadsheet.

Think spreadsheet as a databalse table.

The solution is a locking system.

The locking system has 2 lock types:
- shared locks (read locks): clients can read at the same time
- exclusive locks (write locks): block both read locks and other write locks, allow only a single client at a given time.

### Lock Granularity

One way to impove the concurrency of a shared resource.
Don't lock the entire resource.
Lock only the part contains the data you need to change.

Locks are not free, a lock operation needs:
- getting a lock
- checking a lock is free
- releasing a lock
- ...

If the system speends too much time managing locks insteads of storing and retriveing data, performance suffers.

Locks are implemented in the storage engine, not the server.

Table locks:
- Basic
- The lowest overhead

Row locks:
- Greatest concurrency
- The greatest overhead


## Transactions

A transaction is a group of SQL statements that are treated atomically, as a single unit of work.

A trasaction must pass the ACID test.
- Atomicity - a single unit of either,a transaction is either applied or enver commited.
- Consistency - change affected data only in allowed ways inlcuding constraints, cascades, triggers.
- Isolation - the results of a transaction are invisible to other transaction until the transaction is complete.
- Durability - a transaction's changes are permanent.

### Isolation Levels

Define the rules for wich changes are and aren't visible inside and ouside a transaction.
Lower levels allow higher concurrency and have lower overhead.

READ UNCOMMITED
> Transaction can view the results of uncommited transactions.
> Reading uncommitted data is known as a dirty read.

READ COMMITED
> A transaction can see changes made by commited transactions.
> A transaction won't be visible to others until it has commited.
> The nonrepeatable read issue.

REPEATABLE READ
> Ensures that any rowns a transaction reads will look the same in subsequent reads withing the same transaction.
> The phantom reads problem can occur.

The phantom example, you select a range with `where age < 10`, you get 1 row.
another transacton inserts a new row into the range, you select a again with `where age < 10`, you get **2 rows**.

SERIALIZABLE
> Sovles the phantom read problem by forcing transaction to be ordered so they can't conflict.
> SERIALIZABLE locks every rows it reads.
> A lot of timeouts and lock resources.

### Deadlocks

A deadlock is when two or more transactions are mutually holding and requesting locks on the same resources,
creating a cycle of dependencies. 

The database solves the deadlock by deadlock detections and timeouts.

### Transaction Logging

1. Instead of updating the tables on disk each time a change occurs, the storage engine changes its in memory
copy of the data. This's very fast.
2. Then it writes a record of the change to the **transaction log**, realivey fast.
3. Then at some later time, a process update the table on a disk.

Write-ahead logging technique

### Transaction in MySQL

Storage engines drive how data will be stored and retrived from disk.

By default, a single INSERT, UPDATE, DELETE statement is wrapped in a transaction and committed immediately.
This is known as `AUTOCOMMIT` mode.

Some DLL commands cause MySQL commit the transaction during an open transaction.

MySQL lets you set isolation levle using `SET TRANSACTION ISOLATION LEVEL`, which takes effect when the
next transaction starts.

Transaction mangement is in the storage engine level, so you can't mix them.

Implcicit locking: InnoDB can acquire locks at any time during a transaction, doesn't not release them until a `COMMIT` or `ROLLBACK`.

Explicit locking: 
- SELECT ... FOR SHARE
- SELECT ... FOR UPDATE
