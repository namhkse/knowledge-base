# Chapter 3. Performance Schema

# Introduction to Performance Schema

Are your queries running faster than before?
Are locks slowing down the application?
Did memory usage change?

Performance Schema is a database that stores the data required to answer these questions

Performacne Schema provides low-level metrics on operations running inside MySQL server.

Instruments - refer to any MySQL code that we want to capture information about.
For example, if we want to collect information about locks, we need to enable the `wait/lock/metadata/sql/mdl` instrument.

Consumer - a table that stores the information in Performance Schema about what code was instrumented.

## Instrument Elements
```sql
select * from performance_schema.setup_instruments;
```
The `setup_instrument` table contains a supported instruments.

## Consumer Organization

A cunsomer is the destination where an instrument sends its information.

110 consumer tables, 5 groups
- Current and historical data: contains events
- Summary tables and digest: summary tables hold aggregated information that allows you to find ineffient quries, and workload.
- Instances : objects that instruments are monitoring
- Setup: setting for runtime setup of `performance_schema`
- Other tables

## Resource Consumption

The data collected by Performance Schema is kept in memory.

The actual impact on CPU utilizaton depends on the specific instrument.

## Limitations

- It must be supported by a MySQL component
- It collects data only after the specific instrument and consumer are enable.
  For example, a server with all instrumentation diabled, you can't investigage instrument memory usage.
- It is difficult to free memory
  You can litmit the size of consumers and leave them autosized.

## sys Schema

sys schema has only of views and stored routines over `performance_schema`.

## Understanding Threads

MySQL server is multithreaded software.

```sql
SELECT NAME, THREAD_ID, PROCESSLIST_ID, THREAD_OS_ID
FROM threads;
```

OS thread ID and internal MySQL thread ID that is `THREAD_ID` in `performance_schema` tables.

# Configuration

A few portions of Performance Schema can only be changed at server startup: enabling or disabling of Performance Schema.

## Enabling and Disabling Performance Schema

The SQL used to see Performance Schema is enable or disable.
```sql
SHOW VARIABLES LIKE performance_schema
```

Edit the configuration files to enable/disable Performance Schema.

## Enabling and Disabling Instruments

```sql
SELECT NAME, ENABLED
FROM setup_instruments
WHERE NAME = 'statement/sql/select'
```
You can enable or disable in 3 ways:
- Edit `setup_instruments`.
  This method doesn't persist between restart.

- Use `ps_setup_enable_instrument` and `ps_setup_disable_instrument` in `sys`.
  This method doesn't  persist between restart.

- Use startup parameters
  Persist betwen restart

  ```sh
  mysqld \
  --performance-schema=ON \
  --performance-schema-instrument='instrument_name=value'
  ```

## Enabling and Disabling Consumers

3 ways:
- Updating the `setup_consumers` table in `performance_schema`.
- Using `ps_setup_enable_consumer` and `ps_setup_disable_consumer`. 
- Setting configuration parameter.

## Tuning Monitoring for Specific Objects

Enable and disable monitorign for specific objects type. This is done in the `setup_objects` table.

## Tuning Threads Monitoring

The `setup_threads` table contains a list of backgrond threads that could be monitored.

Monitor user threads by setting in `setup_actors`.
```sql
INSERT INTO performance_schema.setup_actors
(HOST, USER, ENABLED, HISTORY)
VALUES ('localhost', 'sveta', 'YES', 'NO'),
('example.com', 'sveta', 'YES', 'YES'),
('localhost', '%', 'NO', 'NO');
```

This SQL configures which hosts/users should be instrumented by Performance Schema.

## Examining Read Versus Write Performance

A SQL routine is a piece of SQL logic that saved inside the database and can be executed later.
- Stored procedure
- Stored function

```sql
SELECT
    THREAD_ID,
    EVENT_ID,
    SQL_TEXT,
    TIMER_WAIT / 1000000000000 AS seconds,
    ROWS_EXAMINED,
    ROWS_SENT
FROM performance_schema.events_statements_history
WHERE SQL_TEXT IS NOT NULL
ORDER BY TIMER_WAIT DESC;
```

Columns in event_statement_history can be used as indicators for optimization:
- SELECT_FULL_JOIN - High
- SELECT_FULL_RANGE_JOIN - High
- SELECT_RANGE - Low
- SORT_ROWS - Medium

For example, to find all the queries that do not use a good index

```sql
SELECT THREAD_ID, SQL_TEXT, ROWS_SENT, ROWS_EXAMINED, CREATED_TMP_TABLES,
NO_INDEX_USED, NO_GOOD_INDEX_USED
FROM performance_schema.events_statements_history_long
WHERE NO_INDEX_USED > 0 OR NO_GOOD_INDEX_USED > 0;
```

To find all the queries that created temporary tables, run:

```sql
SELECT THREAD_ID, SQL_TEXT, ROWS_SENT, ROWS_EXAMINED, CREATED_TMP_TABLES,
CREATED_TMP_DISK_TABLES
FROM performance_schema.events_statements_history_long
WHERE CREATED_TMP_TABLES > 0 OR CREATED_TMP_DISK_TABLES > 0;
```

### Using sys schema

The sys schema provides views that could be used to find problematic statement.

`statement_with_errors_or_warning` lists all statement with errors and warnings
For example, you will see the wrong sql `SELECT * FROM non_existed_table`.

`statement_with_full_table_scans` lists all statemnts that requires a full table scan.

`prepared_statements_instances` table contains all prepared statements existing in the server.
Unlike in teh events_statement_* tables, statistics data is summed.
Note that if you drop the prepared statement, statistis are deleted.


**Statements profiling**   
The events_stages_[current|history|history_long] table contains profiling information.
Such as how much time MySQL spent while creating a temp table, updating, or waiting for a lock. 

Enable `stage/*` patterns

```sql
-- Which stage of the query execution took a critically long time?
SELECT eshl.event_name, sql_text,
eshl.timer_wait/10000000000 w_s
FROM performance_schema.events_stages_history_long eshl
JOIN performance_schema.events_statements_history_long esthl
ON (eshl.nesting_event_id = esthl.event_id)
WHERE eshl.timer_wait > 1*10000000000;
```

## Examining Metadata Locks

Tables: metadata_locks
Holds locks that are set by different threads.

Shared metadata locks are set for any SELECT, UPDATE, and so on

Locks are held until the transaction finishes.
DDL statement implicitly commit transactions.
