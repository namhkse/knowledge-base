# Chapter 7. Stateful Streaming

Most applications will need to maintain some state for processing.

# State Stores and Materializing State from an Event Stream

Materialized state: a projection of events from the source event stream - Immutable

State store: where your service's business state is stored - Mutable

Where does each microservice store its data ?
- Interally: memory, disk
- Externally: external storage service

# Recording State to Changelog Event Stream

A changelong is a record of all changes made to the data of the state store.

As a copy of the state maintained outside of the emicroservice instance, the changelog can used
to rebuild state.

> TIP: 
> The task of rebuilding failed services can be optimized with changelogs.

For examle: a state store with changelogging enabled

Event stream put(key, value):
- put(5, cat)
- put(2, van)
- put(1, cow)
- put(5, hat)

Table store (key, value)
- 5, hat
- 2, van
- 1, cow

Changelog:
- | 5, cat | 2, van | 1, cow | 5, hat |

The newly created application instance just needs to load the data from teh changelog partitions.

Changelogs are build in feature or implemented by the application.

Basic producer/consumer clients tend not to provide any changelogging or state support.

# Materializing State to an Internal State Store

Internal state stores are in the same container, or on the sam eunderlying hardware.

A microservice instance, its assigned partitions, state stores.

Avoid multipel sources of truth, 1 partition has only 1 state store.

RocksDB is used to implement internal state stores.

## Materializing Global State

A global state store is special form of the internal state store.

A global state store the data of the all partitions for a given stream.

## Advantage of Using Internal State

- Scalability requirements are offloaded from the developer
- High-performacne disk-based options
- Flexibiblity to use a network-attached disk

## Disadvantages of Using Internal State 

- Limited to using runtime-defined disk.
- Wasted disk space

## Scaling and Recovery of Internal State

The new or recovered instance needs to materialize any state before it can begin processing
new events.

The quicklest way is to reload the changelog topic.

### Using hot replicas

A single replica of materialized state for each partition.

### Restoring and scaling from changelogs

Consuming from the changelog.

### Restoring and scaling from input event streams

If no changelog is maintained, the microservice instance can rebuild its state stores
from the input streams.

This process takes much logger to rebuild state than restorign from a changelog.

# Materializing State to an External State Store

Outside of a microservice's container, but typicallly located within the same local network.

Relation databases, key/value stores.

Sharing materialized state is a common anti-pattern.

## Advantages of External State

- Full data locality
- Technology

## Drawbacks of External State

- Mangement of multiple technologies
- Performance loss due to network latency

## Scaling and Recovery with External State Stores

### Using the source streams

Consuming events from the beginning of time from the source streams creates a fresh copy of the 
state store.

The logest downtime.

### Using changelogs

They rebuild the entire state as stored in the changelog before resuming processing.

### Using snapshots

It is typical for external sstates to provide their own backup and restoration process.

# Rebuilding Versus Migrating State Stores

Changes to existing state store data structures.
- Add new information to existing events.
- Add some extra steps to materialized table

In such cases, the existing state store will need to be updated.

## Rebuilding

Rebuilding state stores is the most common method.

Steps:
1. Stop the microservice
2. Reset the consumer input stream offset to beginning.
3. Delete intermediate states are stored in changelog or the external state store.
4. Start the new version of the microserce.

## Migrating

Large state stores can take a long time to rebuild.

For a state store backed by a relation database, you'd just need to update the business logic
alongside the associated table definition.

# Transactions and Effectively Once Processing

Exactly once processing.

A microservice may process the same data multiple times becuase it fail to commit its offsets.

The processing logic will be executed, it may incude side effects.

Idempotent writes are supported feature among event brokers.
An event is written once and only once to an event stream.

Transactions may be supported by event brokers.
The atomic writing.

## Effectively Once Processing With Client-Broker Transactions

Effectively once processing can be facilitated by any event broker that
support transactions.

A transaction contains:
1. Ouput events.
2. Updates made to internal state backed by a changelog.
3. The incrementing of the consumer offsets.

For examle:

Stream - Stock changes key, value, offset
- ID1, +5, 1
- ID1, +1, 2    - We are here
- ID1, -2, 3
- ID1, +3, 4

Atomic transaction:
1. Offset commit: AppId, 2
2. Changelog commit: ID1, 6
3. Output event: ID1, 6

## Effectively Once Processing Without Client-Broker Transactions

Not support client-broker transactions.

First, the upstream may produce duplicate records.
Second, the downstream may execute duplicated processing events.

> TIP:
> It is better to use an event broker and clietn that support idempotent writes.

### Generating duplicate events

A producer successfully writes the events to an event stream, but fails to receive a write ACK,
and retries or crashes before updating consumer offsets (a microservice is both a producer and consumer.)

### Identifying duplicate events

First, do duplicate events cause serious problems ?
- Yes
- No

In the case no, you can ignore it.

In the case yes, you will need to identify them.
One way to od this is to have the producer generate a unique ID for each event.

A uique ID is created by a hash function that uses keys, values, creation time.
A fiew scenarios:
- A bank account transfer.
- An ecommerce order.

### Guarding against duplicates

Any effectively once consumer must either identify and discard duplicates, perform idemptent
operations.

This requires each consumer maintain a state store of processed IDs.
