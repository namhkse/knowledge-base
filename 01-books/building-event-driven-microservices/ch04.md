# What Is Data Liberation?

Data liberation is the identification and publiscation of cross-domain data sets to their
coresponding event streams and is part of a migration strategy for event-driven architectures.

Cross-domain data sets include any data stored in one data store that is required by other
external systems.

Poit-to-point dependencies between servcies and data stores, often highlight the 
cross-domain data that should be liberated.
              
              |----- Query ------> System A
Legacy system |----- Query ------> System B
              |----- Query ------> System C

Data liberation enforces 2 primary features of event-driven architecture:
- the single source of truth
- the elimination of direct coupling between systems.

# Liberating Data by Query

Query based data liberation involves querying the data store and emitting selected results to
an associated event stream.

There are serveral types of queries
1. Bulk Loading
    Load all of the data from the data set.
    When teh entire table needs to be load at each polling.
    Expensive

2. Incremental Timestamp Loading
    Load all data since the highest timestamp of the previous query's results
    Uses an `updated_at` column.

3. Autoincrementing ID Loading
    Query all data larger than the last value of the ID.
    Only records with an ID larger than the last processed ID are queried.

4. Custom querying
    The client requires a certain subset of data from a larger data set, or
    when joining multable tables to avoid over-exposure the internal data model.

5. Incremental Updating
    Its important to consider whether the interval between requests is sufficient to finish
    loading all of the data. Begining a new query while the old one is still loading
    can lead to race conditions.

Benefit of query-based updating:
- Customizability
- Independent polling periods
- Isolation of internal data models

Drawback of query-based updating:
- Required updated-at timestamp
- Untraceable hard deletions
- Production resource consumption

# Liberating Data Using Outbox Tables

An outbox table contains change made to the internal data of a dat store, with each
significant update stored as its own row.

Whenever an insert, update, or delete is made to one of the data store.
Each table under change-data capture can have its own outbox table, or a signle outbox can be used
for all changes.

Both the internal table updates and the outbox updates must be bundled into a single
transaction.

The records in outbox table smust have a strict ordering identifier.

One of the major benefits of the outbox is taht the data store clietn can isolate the internal
data model from dwonstream consumers.

An event needs multiple tables, tables are nomoalize.

Eventification: converts highly normalized relational data inot easy-to-consume single event updates.

For example:
The User has a FK to the City and Country.
A dowstream consumer wants everything about each user in a single event.
Instead of being forced to materialize each stream (user, city, country) and denormalize it.
The source produce normalized events.

Serialzing before writing to the outbox
Benefit: simple, the strongest consistency
Drawback: serialization overhead.

Serializing after writing to the outbox.
Drawback: a failure to serialize from the outbox table, can't publish events.
Because the transaction is commited, difficult to maintain.

> TIP
> Before teh fact serialization provides a stronger guarantee.

Benefits of event-production with outbox tables
- Multilanguage support
- Before-the-fact
- Isolation of the internal data model
- Denormalization

Drawbacks of event production with outbox tables
- Required application code changes
- Business process performance impact
- Data store perforamce impact 

Using trigger to insert a record to the outbox table.

Benefits of using triggers:
- Supported by most databases
- Low overhead for small data sets
- Customizable logic

Drawback of using triggers:
- Performance overhead
- Change management complexity
- Poor scaling
- After-the-fact schema enforcement.

# Sinking Event Data to Data Stores

Sinking dat aform event streams consists of consuming event data and inserting it into a data store.

Useful for integrating non-event-driven applications with event streams.

The sink process reads the event streams from the event broker and insert the data into the data store.
