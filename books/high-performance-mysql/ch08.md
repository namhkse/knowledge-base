# Query Performance Optimization

Schema optimization and indexing are necessary for hight performance.
But they aren't enough.

# Why Are Queries Slow?

It's all about response time.

Quries are tasks, but they are composed of subtasks, and those subtasks
consume time.

To optimize a query, you must optimize its subtasks by eliminating them.

Parsed, planed, and executed.

It involves lots of calls to the storage engine to retrieve rows,
as well as operations such as grouping and sorting.

# Slow Query Basics: Optimize Data Access

The most basic reason a query doesn't perform well is because its working 
with too much data.

Analyze a poorly performing query in two steps:
1. Find out whether your application is retriveing more data than you need.
You access too many rows or colloumns.
2. Find out whether the MySQL server is analyzing more rows than it needs.

# Are you asking the Database for Data you don't need?

Fetching more rows than needed.
    Fetching the 100 most recent articles for a news site when they
    only need to show 10 of them on the front page.
    The best solution is to add a LIMIT clause to the query.

Fetching all columns from a multitable join.
   If you want to retrive all actors who appear in the film Academmy Dinosaur. 
   ```sql
    SELECT * FROM sakila.actor
    INNER JOIN sakila.film_actor USING (actor_id)
    INNER JOIN sakila.film USING (film_id)
    WHERE sakila.film.title = 'Academy Dinosaur';
    -- Time: 352ms
   ```
   Notice the `*`, it has more colums than we need.
   Fix: `SELECT sakila.actor.* FROM sakila.actor ...;`
   Now it takes `300ms`

Fetching all columns.
    You should always be suspicious when you see `SELECT *`.
    Using `*` can avoid some you alters the table's column.

Fetching the same data repeatedly
    If you are not careful, it's quite easy to write application code 
    that retrieves the same data repeatedly from the database server.

# Is MySQL Exampining Too Much Data

Once you are sure your queries retrieve only the data you need, you can look
for queries that examine too much while generating reuslts.

The simplest query cost metrics are:
- Response time
  Response time = service time + queue time
  Service time is how long it takes the server to process the query
  Queue time is the portion of response time during the server isn't 
  really executing the query.
  
  Prefer considering I/O and lock

- Number of rows examined and returned
  
- Rows examined and access types
  When you're thinking about the cost of a query, consider the cost
  of finding a single row in a table.
  The access method(s) appear in the type column in EXPLAIN output.
  - Full table scan
  - Range scans
  - Unique index lookups
  - Constants

```sql
SELECT actor_id, COUNT(*)
FROM sakila.film_actor
GROUP BY actor_id;
```

This query returns 200 rows, but how many rows does it need to read?
Ouch! Reading 5362 rows.
An index can't reduce the number of rows examined for a query like this
one because there's no WHERE clause to eliminate rows.

# Ways to Restructure Queries

## Complex Queries Versus Many Queries

Prefer to break up a complex query into several simpler queries.
Reduce overhead of query parsing and optimization stages.

## Chopping Up a Query

Instead delete many rows, split it to chunk
20_000 rows -> 20 times, each time delete 1000 rows
Reduce lock rows, and transaction log

## Join Decomposition

Decompose a join by running mulitple single-table queries instead of
a multible join and then performing the join in the application.

SELECT * FROM tag
JOIN tag_post ON tag_post.tag_id=tag.id
JOIN post ON tag_post.post_id=post.id
WHERE tag.tag='mysql';
You might run these queries:
SELECT * FROM tag WHERE tag='mysql';
SELECT * FROM tag_post WHERE tag_id=1234;
SELECT * FROM post WHERE post.id in (123,456,567,9098,8904);

Why this is better
- Caching, applications cache objects, if the result is cache, we can skip
query.
- Executing the queries can someitmes reduce lock.
- Join in the application makes it easier to scale the database by
table on different servers.
- You can reduce row accesses.
