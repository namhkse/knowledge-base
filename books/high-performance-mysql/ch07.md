# Chapter 7. Indexing for High Performance

Indexes also called keys in MySQL are data structures that storage engines use to find
rows quickly.

Indexes are critical for good performance and become more important as your data grows larger.

# Indexing Basics

Think about the index of a book.
To find out where a particular topic, you look in the index, and it tells you the page
number(s) where that term appears.

```sql
SELECT first_name FROM sakila.actor WHERE actor_id = 5
```

There's an index on the column actor_id column, so MySQL use the index to find 
rows whose actor_id is 5. It performs a lookup on the values in the index and 
returns any rows containing the specified value.

An index contains values from one ore more column.

If you index more than one column, the column order is very important because MySQL
can only search efficiently on the leftmost prefix of the index.

Create an index on 2 columns is not the same as creating 2 separate single-column indexes.

ORMs rarely produce index-friendly queries unless you use them for only most basic types
of queries, such as primary key lookups.

## Types of Indexes

Indexes are implemented in the storage engine layer, not the server layer.
They work slightly differently in each engine, and not all engines support all types of
indexes.

Let's look at the two most commonly used index types MySQL currently supports.

### B-tree indexes

B-tree index uses a B-tree data structure to store its data.
Most of MySQL's storage engines support this index type.

The general idea of a B-tree is that all the value are stored in order,
and each leaf page is the same distance from the root.

Leaf pages are special because they have pointers to the indexed data instead of pointers
to other pages.

```sql
CREATE TABLE People (
    last_name varchar(50) not null,
    first_name varchar(50) not null,
    dob date not null,
    key(last_name, first_name, dob)
);
```

Adpative hash index: The InnoDB storage engine has a special feature called adaptive
hash indexes. When InnoDB notices that some index values are being accessed very
frequently, it builds a hash index for them in memory on top of B-tree indexes.
You can't contorl or configure this processes.

Type of quereis that can use a B-tree index: B-tree indexes work well for lookups by
the full key value, a key range, or key prefix. 
They are useful of the lookup uses a leftmost prefix of the index.

Match the full value
    Specifies values for all columns in the index.
    For example, this index find a person named Cuba Alen who was born on 1990-01-01

Match a leftmost perfix
    This index find all people with the last name Allen.

Match a column prefix
    This index can help you find all people whose last names begin with J.

Match a range of value
    This index can help you find people whose last names are betwen Allen and Barrymore.

Match one part exactly and match a range on another part
    This index can help you find everyone whose last name is Aleen and whose first name
    starts with the letter K.
    This is an extract match on last_name and a range on first_name
    
Index-only queries

Limitations of B-Tree indexes   
- They are nto useful if the lookup does not start from the leftmost side of the indexed
columns.
For example, this index won't help you find all people named Bill or All people born on a
certain date, because those column are not leftmost in the index.
You can't use the index to find people whose last name ends with a particuar letter.

- You can't skip columns in the index.
You can't find a people whose last name and were bon in a date. If you don't specify
a value for the first_name column. MySQL can use the first column of the index.

- The storage engine can't optimize accesses with any columns to the right of the
first range condition. 

WHERE last_name="Smith" AND first_name LIKE 'J%' AND dob='1967-12-13'

The first range condition is `first_name LIKE 'J%'`.
dob in the right of the first range condition can't be optimize accesses.

There limitatons are all related to column ordering.
For optimal, you may need to create indexes with the same column in different orders to
satisfy your queries.

Full-text indexes

FULLTEXT is a special type of index that finds a keywords in the text instead of comparing values to the vlaues in the index.

Full-text indexes are for MATCH AGAINT operations not ordinary WHERE clause operations.

Benefits of indexs
- navigate quickly to a position in the table.
- indexes stores a copy of the values, so some queries can be satisfied from the index alone.
- Indexes turn random I/O into sequential I/O.

## Prefix Indexes and Index Selectivity

Save space and get good performance by indexing the first few characters instead of the whole
value. This make your indexes use less space, but it also makes them less selective (number of distinct indexed values / total number of rows in the table).

High selective index is good.

MySQL disallows indexing their full lenght on TEXT, BLOB.
