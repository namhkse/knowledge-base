## Fact Table

Facts represent business activities that have aleady happened.
Facts are similar to the notion of domain events.

Facts represent activies of business processes.
For example, a fact table `Fact_CustomerOnboradings` contains a record
for each new onboared customer and `Fact_Sales` a record for each commited sale.

```
Fact_SolvedCases
PK  CaseId
FK  AgentKey
FK  CategoryKey
FK  OpenedOnDateKey
FK  ClosedOnDateKey
FK  CustomerKey
```

Fact records are nerver deleted or modified.
They are append-only data, teh only way to express that current data is outdated is to append
a new record with the current state.

Operational systems require teh most precise data to handle business transactions.

## Dimension Table

The dimensions are designed to describe the facts' attribute and are refeerenced as
a FK from a fackt table to a dimension table.

The attributes modeled as dimensions are any measuements or data that is repeated accross 
different fact records and cannot fit in a signle column.

# Analytical Data Management Platforms

Two common analytical data architectures: data warehouse and data lake.

## Data Warehoust

The DWH architecture is relatively straightforward.
Extract data from all of the enterprise's operational systems, transform the source data
into an analytical model, and load the resultant data into data analysis-oriented database.
This database is the data warehouse.

This data management architecture is based priamrily on the ETL scripts.
The data can come from: 
- operational database
- streaming events
- logs
- ...

In addition to translating the source data into fact/dimensions-based model, the
transformation step may include additional operations such as removeing sensitive data,
deduplicating records, reorder events, aggregating fine-grained events, and more. 

In some cases, the transformation may require temporary storage aka **the staging area**.

The heart of the DWH architecture is the goal of building an enterprise-wide model.
The model should address all of the different use cases for analytical data.
optimizing the business, reducing operational costs, making intelligent business decisions,
reporting, and training ML models.

A data mart is a database that holds data relevant for well-defined analytical needs, such
as analysis of a single business department.

2 ways to create data marts.
- A data mart is populated directly by an ETL process from an operational system.
    - CHALLENGE: query data accross differnt marts
    - CHALLENGE: cross-mart query
- while another mart extracts its data from the data warehouse.
    - CHALLENGE: all-encompassing model

Another challenging aspect is the ETL processes create a strong coupling between the OLAP
and the OLTP.

A slight change in the schema is destined to break the data warehouse’s ETL scripts. 

## Data Lake

A data lake–based system ingests the operational systems’ data. However, instead of being transformed right away into an analytical model, the data is persisted in its raw form, that is, in the original operational model.

The raw data cannot fit the needs of dta analysts. As a result, it is the job of
the data engineers and the BI engineers to make sence of the data in the lake and
implement the ETL scripts that will generate analytical models and feed them
into a data warehouse.

Operational database -- Ingest -> Data lake -- Extract -> Transform -- Load --> DWH --> Analysis, Reports

The data lakes are schema-less—there is no schema imposed on the incoming data—and there is no 
control over the quality of the incoming data.

# Data Mesh

The data mesh architecture is, in a sense, domain-driven design for analytical data. As the different patterns of DDD draw boundaries and protect their contents, the data mesh architecture defines and protects model and ownership boundaries for analytical data.

Data mesh has 4 rules.

## 1. decompose data arround domains

Both the data warehouse and data lake approaches aim to unify all of the enterprise’s data into one big model. The resultant analytical model is ineffective for all the same reasons as an enterprise-wide operational model is. Furthermore, gathering data from all systems into one location blurs the ownership boundaries of the various data elements.

Thsi use multipel analytical models and align them with the origin of the data.
Analytical models with the bounded contexts's boundaries.

Each bounded context now owns its operational (OLTP) and analytical (OLAP) models.

## 2. Data as a product

The analytical data through well-defined output ports,

Analytical data should be treated the same as any public API:
- it should be easy to disover the endpoints
- well-defined schema describing the served data, its format
- truthworthy source, as with any API (authentication), SLA(avilability, freshness, latency, data quality)
- The analytical model should be versioned as a regular API and correspondingly manage integration-breaking changes in the model.
