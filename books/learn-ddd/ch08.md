# Ports & Adapters

The presentation layer and data access layer represent integration with external components:
databases, external services and UI frameworks.

Let's unify all such infrastructural concers into a single "Infrastructure layer"

Infrastructrual Layer:
- Database
- UI framework
- Expternal provider
- Message bus

## Dependency Inversion Principle

The business logic should not depend on low-level modules.

In the traditional layerd architecture. The business layer depends on the infrastructra layer.
To conform with the DIP, let's reverse the relationship, as below

Infrastructural layer --> Business logic layer

Finally, let's add an appliction layer.

Infrastructural layer --> Application Layer --> Business logic layer

## Integration of Infrastructural Components

The core goal the port and adapters architecture is to decouple teh system's business logic 
from its infrastructural components.

Instead of referencing and calling the infrastructural components directly, the business logic
layer defines "port" that have to be implemented by the infrastructral layer.

The infrastructure layer implements "adapters": concrete impelmentation.

```cs
// App.BusinessLogicLayer
public interface IMessaging {
    void Publish(Message payload);
    void Subscribe();
}

// App.Infrastructure.Adapters
public class SQSBus : IMessaging {...}
```

## Variants

The port & adapters architecture is also known as hexagonal architectura, onion architecture,
clean architecture.

Application layer = service layer = use case layer
Business logic layer = domain layer = core layer

# CQRS

This pattern enables representation of the system's data in multiple persistent models.

## Polyglot Modeling

It may difficult to use a single model of the system business domain.

For example, onilne transacton processing and analytical processing require different representations
of the systems' data.

## Implementation 

There are two types of models: 

### the command execution model

Operations that modify the system's state.
This model is used to implement the business logic, validate rules, and enforce invariants.

### the read model

The system can define as many models as needed to present data to users or supply information information to other system.

Read models are read-only.

## Projecting Read Models

For the read models to work, the system has to project changes from the command execution model
to all its read models.

Similar to the view table in database: whenever source tables are updated, the changes have to 
be refected in the precached views.

Two way to generate projections: sync and async

### Sync projections

1. The projection engine quries the OLTP database for added or updated after the last processed checkpoint.
2. The project engine uses the updated data to regenearte/update the system's read models.
3. The projection engine stores the checkpoint of the last processed record.

### Asynchornous projections

The command execution model publishes all commited changes to a message bus.

# Challenges

Performance advantages of the async projection method, it is mor eprone to the challenges of distirubted
computing.

If the messages are processed out of order or duplicated, inconsisten data will be projected into the read models.

> Prefer sync projection.
