# Chapter 4. Integrating Bounded Context

A language in one bounded context can model the business domain to solve a particular problem.
Another bounded context can represent the same business entities but model them to solve a different problem.

Models in different bounded contexts can be evolved and implemented independently.
Models have to integrate without another.

There will  always be touchpoints between bounded contexts. These are called **constracts**

# Cooperation

Cooperation patterns relate to bounded contexts implementd by teams with well-established 
communication.

These are bounded contexts implemented by a signle team.

## Partnership

The integration between bounded context is coordinated in an ad hoc manner.
One team can notify a second team about a change in the API, the second team will cooperate and
adapt

Bounded context 1 -- Patters --> Bounded context 2

## Shared Kernel

Despite bound contexts being model boundaries, there still can be cases when the same model
of a subdomain, or part of it, will be implemented in multiple bounded contexts.

For example, authorization models are shared kernel

### Shared scope

A change made to the shared model has an immediate effect on all bound contexs.
Hence, to minimize the cascading effect of change.

### Implementation

Any modifications will reflect in all bounded contexts immediatly.

Mono-repository, same source files referenced by multiple bounded contexts.

Shared repository, linked library.

### When to use shared kernel

The cost of duplication versus the cost of coordination.

When the cost of duplication is higher than the cost of cooridation.

Frequently change -> the higher integration costs

## Customer - Supplier

UPSTREAM: One of bounded contexts - the supplier provides a service for its customers.
DONWNSTREAM: The customer or consumer is downstream.

### Conformist

The upstream team provides the integraiton constract, defined its own model, take it or leave it.
The downstream can accept the upstream team's modeli. That relation is called **conformist**.

### Anticorruption Layer

Downstream bounded context is not willing to conform.
Intead, it can translate the upstream bounded context's model into a model tailored to its own needs via an anticorruption layer.

Bounded context 1 <--- ACL -- Bounded context 2

The ACL addresses sceneartios:
- When the downstream bounded context contains a core subdomain
- When the upsteam model is inefficeient or invonventient for the consumer's needs
- When the supplier's contract changes offten

## Open-Host Service

The power is skewed toward the consumers.
The upstream provides the public interface/protocol.

For example:
Upstream: Ordering Context has REST API `GET /orders/{id}`
