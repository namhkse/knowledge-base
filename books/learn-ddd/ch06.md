# History

# Domain Model

The domain model pattern is intended to cope with cases of complex business logic.

Instead of CRUD interfaces, we deal with complicated state transitions, business rules,
and invariants: rules that have to be protected at all times.

# Implementation

A domain model is an object modle of th edomain tha tincorporate both behavior and data.

DDD's tactical patterns 
- aggregates
- value objects
- domain events
- domain services

are the building blocks of such an object models.

They put the business logic first.

## Complexity

The domain's busines logic is already complex, so the objects used for modeling it should not 
introduce any complexities liek infrastructural or technological concers.

## Value object

A value object is an object that can be identified by the commpositon of its values.
For example:
```cs
class Color {
    int red;
    int green;
    int blue
}
```
No explcit ID field need to identify colors.

## Ubiquitous language

Relying on the language standard librarys' primitive data types such as strings, integers or dic
to represent concepts of the business domain is knwon as the primitve obsession code smell

First, notice the increased clarity.
The `country` variable, there is no need to elaborately call it `countryCode` to communicate the intent of it. The value object makes the intent clear, event with shouter varialbe names.
The value object is `CountryCode`.

Second, there is no need to validate the user before the assign.
Teh validation logic resides in the value objects themselves.
Value objects shine brightest when they centralize the business logic that manipulates the values.

## Implementation 

Value objects are immutable objects.
Therefore, when an executed action results in a new value object.

```cs
class Color {
    public readonly byte Red;   // Notice this line
    public readonly byte Green;
    public readonly byte Blue;
    ...

    public Color MixWith(Color other) {
        // Return a new object
        return new Color(
            red: Math.Min(this.Red + other.Red, 255),
            green: Math.Min(this.Green + other.Green, 255),
            blue: Math.Min(this.Blue + other.Blue, 255),
        )
    }
}
```

Value objects dont' have IDs. They need to be override the equality checks.

## When to use value objects

The simpler answer is, whenever you can.
They are immutable, free of side efects and thread safe.

# Entities

An entity is the oposite of a value object.
It requires an ID field to distinguish between the different instances of the entity.

For example different two people can have same name.

```cs 
class Person {
    public readonly PersonId Id;
    public Name name {get; set;}
}
```

The ID should be immutable throghout the entity's lifecycle.

The entites are expected to change.

## Aggregates

An Aggregate is an entity:
It requires an ID field, states. It is expected to change during an instance's lifecycle.

## consistency enforcement

Aggregate's state can be mutated.
The aggregate's logic has to validate all incoming modificatins and ensure that teh changes do not 
contradict its business rules.

The state-modifying methos expoed as an aggregate's public interface are refered to as commands.

The command can be implement in 2 ways:
- public method
```cs
public class Ticket {
    ...
    public void AddMessage(UserId from, string body) {
        var message = new Message(from, body);
        _message.Append(message);
    }
}
```
- paramether object
```cs
public class Ticket {
    ...
    public void Execute(AddMessage cmd) {
        var message = new Message(cmd.from, cmd.body);
        _message.Append(message);
    }
}
```

Prefer parameter command + polymorhic method `Execute`.

This make the application alyer that orchestrates operations on aggregates rather simple.

```cs
public ExecutionResult Escalate(
    TicketId id,
    EscalationReason reason) 
{
     try {
        var tiket = _ticketRepo.Load(id);

```

Aggregates support concurrency management, they should hold a version.

```cs

    TicketId _id;
    int _version;
}
```

When committing a change to the database we have to ensrue that version

Concurrency management can be implemented elsewhere beshides a relation database.

## Transaction boundary

Since an aggregate's state can only be modified by its own business logic, the aggregate also
acts as an transactional boundary.

no system operation can assume a multi-aggregate transaction.
A change to an aggregtee's stte can only be commited individually, one aggreage per database transactoion.

The one aggregate instance per transaction forces us ot carefully design an aggreagtes boundaries,
ensrue that the design address the business domain's invariants and rule.
The need to commit chages in multiple aggregaes signalrs a wrong transacition boundary, and hence, wrong
aggregate boundaries.

## Hiearchy of entities

There are scenarios in which mulitple objects should share a transaction boundary.
For example when both can be modified simultaneously or the business rules of one object depend
on the state of another object

Ticket 1 --- * Message 1 --- * Attachment

The aggregate pattern resembles a hierarchy of entites, all sharing transactional consistency.
It aggregates business entities, and value objects that belong to the same trasaction boundary.

## Referencing other aggregates

Since all objects contained by an aggregate share the same transactional boundary, performacne
and scalability isssues may arise if an aggreage grows too large.

Only the informatin tha tis required by the aggregate's business logic to be strongly consistent
shoudl be a part of the aggregate.

All information that can be eventually consistent shoudl reside outside the aggregate's bounary.

> The rule of thumb
> Keep the aggreates as small as possible and inlcude only objects that are required to be in
> strongly consistent state by the aggregate's business logic.

```cs

    private UserId customer;
    private List<ProductId> products;
    private UserId assignedAgent;
    private List<Message> messages;
}
```

## The aggregate root

An aggregate represetns a hierarchy of entities, only one of them should be designed as
the aggregate's public interaface - the aggregate root

In addition to the aggregate root's public interface, there is another mechanism through which the
outer world can communicate with aggregates: domain events.

### Domain events

A domain event is a message describing a significant event that has occured in teh business domain.

- Ticket assigned
- Ticket escalated
- Message received.

The name should be formulated in the past tense.

The goal of a domain event is to describe what has happened in the business domain and provide all
the necessary data related to the event.

Domain events are part of an aggregate's public interface.
An aggregate publishes its domain events.
Other processes, aggregates, or external systems can subcribe to and execute their own logic
         
Aggreagte --- Domain Event ---- Subscriber
         |___ Domain Event ---- Subscriber

```cs
class Ticket {
    private List<DomainEvent> _domainEvents;

    public void Execute(RequestEscalation cmd)
    {
        if (!this.IsEscalated && this.RemaintingTimePerscetage <= 0)
        {
            this.IsEscalated = true;
            _domainEvent.Append(new TicketEscalted(_id, cmd.Reason));
        }
    }
}
```

## Domain Service

Business logic that either doesn't belong to any aggregate or value object, or seems to be relevant
to multiple aggregates.

A domain service is a stateless object that implements the business logic.

The assigned agetn has a limited time frame in which to propose a solution to the cusotmer.
The tiem frame depends not only the ticket's data but aso on the agent's departmetn policy.
We can't expect the agent to respond during off-hours.

```cs
class ResponseTimeFrameCalculationService {
    public ResponseTimeframe CalculateAgentResponseDeadline(
        UserId agentId,
        Priority priority,
        bool escalated,
        DateTime startTime)
    {
        var pocily = _departmentRepositor.GetDepartmetnPocidy(agentId);
        var maxProcTime = policy.GetMaxresponseTimeFor(priority);

        if (escalated) {
            maxProcTime = maxProcTime * policy.EscaplationFactor;

            startTime, startTime.Add(policy.MaxAgentResponseTime));
        
        return CalculateTargetTime(maxProcTime, shifts);
    }
}
```
