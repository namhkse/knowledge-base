# What Is EventStorming?

EventStorming is a low tech activity for a group of people to brainstorm and rapidly modle
a business process.

EventStorming is a tatical tool for sharing business domain knowledge.

An EventStorming session has a scope: the business process process that the group is intrested
in exploring.

The participants are exploring the process as a series of domain events,
represented by sticky notes, over a timeline.

Step by step, the modle is enhanced with additional concepts - actors, comands, external systems,
and others - until all of its elements tell the story of how the business process workds.

# Who should participate in EventStorming?

Ideally, a diverse group of people should participate in the workshop.
Anyone related to the business domain in question can participate:
- engineers
- domain experts
- product owners
- testers
- UI/UX designer

But this can be challenging for groups of more than 10 participants.

## The EventStorming Process

An EventStorming worksop is usually conducted in 10 steps

### Step 1: Unstructed Exploration

EventStormign starts with a brainstorm of the domain events related to the business domain being explored.

A domain event is somethign interseting that has happened in the business.

For example, unstrucured exploration
- Shipping cost calculated
- Flight fare booked
- Order initialized
- Request declined
- Request approved
- Destinaton chosen
- Notification sent
- Order shipped

All participants grab a bunch of orange sticky notes, write down whatever domain events come to mind,
and sticking them to modeling surface.

No need to worry about ordering events, or redundancy.

The group should continue generating domain events until the rate of adding new ones slows.

### Step 2: Timelines

The participants organize domain events in the order which they occur in the business domain.

The events should start with the "hapy path scenario": the flow that describes a successfull business.

One the happy path is done, alternative scenarios can be added. For example, paths where errors are
encountered or different business decisions are taken.

            Request approved --> Order initialized
Request   / 
submitted \ 
            Request declined --> Customer notified

This step is also the time to fix incorrect events, remove duplciates and add missing events.

### Step 3: Pain Points

Use this broad view to identify points in the process that require attention.
These can be bottlenecks that can be missing documentation, missing domain knowledge.

The pain points are marked with rotated(Diamond) pink sticky notes.

### Step 4: Pivotal Event

Look for significant business events inidcating a change in context or phase.
These are called pivotal events and are makred with a vertical bar diving the events before
alter the pivotal event.

    |                       |                           |                           |
    |                       |                           |                           |
Shoping cart ............ Order     ................. Order     ............... Order
initialized               initialized                 Shipped                   Delivered
    |                       |                           |                           |
    |                       |                           |                           |

Pivotal events are an indicator of potential bounded context boundraies.

### Step 5: Commands

A command describes what triggered the event or flow of event.

Commadns are written on light blue sticky note adn placed on teh modeling space before the event.

Submit order    Order initialized   Shipping cost calculated
Command         Event               Event

If a command is ecuted by an actor in specific role, the actor is added to the command on a small 
yellow sticky note.

### Step 6: Policies

An automation policy is a scenario in which an event triggers the executeion of the command.
In other words, a command is automatically executed when a specific domain event occurs.

Polices are represented as purple sticky notes connecting events to commands

Shipment approved triggers Ship order

### Step 7: Read Models

A read model is the view of data within the domain that the actor uses to make a decision to
execute a command.

The read models are represented by a green sticky notes.

Thr eread models are positioned before teh commands

Shopping cart       Submit order    Order initialized
Read model          Command         Event

### Step 8: External Systems

An external system is defined as any system that is not a part of the domain being explored.
It can execute commands or can be notified about events.

Pink sticky notes

CRM                 Ship order
Extternal system    Command

### Step 9: Aggregates

An aggregate receives commands and produces events.
Large yellow sticky notes, with commands on the left and events on the right

### Step 10: Bounded Contexts

The last step of an EventStorming session is to look for aggregates that are related to each
other, either because they represent colosely related functionality or because they're coupled
through policies.
