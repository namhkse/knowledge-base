# Chapter 15. Event-Driven Architecture

As microservices, EDA is ubiquitous in modern distributed systems.

EDA is often linked to DDD.
EDA is based on events, and events are prominent in DDD

Careless application of EDA can turn a modular monolith into a distributed big ball of mud.

# Event-Driven Architecture

EDA is an architectural style in which a system's components communicate
with one anohter asycchronously by exchanging event messages.

Instead of calling the endpoints synchronously, the components publish events to notify
other system elements of changes in the system's domain.

The component can subcribe to events raised in the system and react accordingly.

> EDA vs event sourcing
> event sourcing is a method for capturing changes in state as a series of events.

Although both EDA and event sourcing are based on events, they are conceptually different.

EDA refers to the communication between services.
Event sourcing happens inside a service.

# Events

In EDA, the exchange of events is teh key communication mechanism for integrating the components
and making them a system.

## Events, Commands, and Messages

An event is a message, but a message is not necessarily an event

Event: A message describing a change that has already happened
Cannot cancel the event.
Muốn "đảo ngược tác động" của một event, ta tạo một action mới để bù/hoàn tác tác động đó.

Command: A message describign an operation that has to be carried out
A command can be rejected, if it is invalid.

|                | Event                | Command                       |
| -------------- | -------------------- | ----------------------------- |
| Ý nghĩa        | **Đã xảy ra**        | **Hãy làm việc này**          |
| Ví dụ          | `PaymentCharged`     | `RefundPayment`               |
| Có thể cancel? | ❌ Không              | Có thể fail/reject            |
| Dùng để        | Thông báo fact       | Yêu cầu action                |
| Trong Saga     | Trigger/state change | Thực hiện action/compensation |

Event: it happened
Commnand: Do this

## Type of events

3 event types

### Event notification

is a message regarding a change in the business domain that other components will react to.

Should not be verbose, the goal is to notify teh interested parties about event.

```json
{
    "type": "paycheck-generated",
    "event-id": "537ec7c2-d1a1-2005-8654-96aee1116b72",
    "delivery-id": "05011927-a328-4860-a106-737b2929db4e",
    "timestamp": 1615726445,
    "payload": {
        "employee-id": "456123",
        "link": "/paychecks/456123/2021/01"
    }
}
```

In a sense, integration through event notification messages is similar to the Wireless Emergency 
Alert (WEA) system in the United States and EU-Alert in Europe (see Figure 15-3). 
The systems use cell towers to broadcast short messages, notifying citizens about public health concerns, safety threats, and other emergencies. 
The systems are limited to sending messages with a maximum length of 360 characters. 
This short message is enough to notify you about the emergency, but you have to proactively use other information sources to get more details.

Security: enforcing the recipient to query for the detailed infomration prevents ahridng sensitive 
information over the messaing infrastructure and require authorization of teh subscribers to 
access the data.

Concurrency:
Due to acynhronous of event-drivent integratoin, the informatio can be stale when it reachs the
subcribers. If the information is sentitive to race conditon, querying allows gettign the up-to-date
state.

In case concurrent cunsomer, where only one subcriber shoudl process an event, the querying process
can be integrated with pessimistic locking.

### Event-carrier state transfer

ECST messages notify subcribers about changes in teh producer's internal state.
ECST message include all the data refecting teh change in the state.

ECST messages can come in two forms. 
The first is a complete snapshot of the modified entity’s state:
```
{
    "type": "customer-updated",
    "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
    "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
    "timestamp": 1615728520,
    "payload": {
        "first-name": "Carolyn",
        "last-name": "Hayes",
        "phone": "555-1022",
        "status": "follow-up-set",
        "follow-up-date": "2021/05/08",
        "birthday": "1982/04/05",
        "version": 7
    }
}
```

When operating large data structures, it may be reasonable to include in the ECST message only the fields that were actually modified:
```
{
    "type": "customer-updated",
    "event-id": "6b7ce6c6-8587-4e4f-924a-cec028000ce6",
    "customer-id": "01b18d56-b79a-4873-ac99-3d9f767dbe61",
    "timestamp": 1615728520,
    "payload": {
        "status": "follow-up-set",
        "follow-up-date": "2021/05/10",
        "version": 8
    }
}
```

> Conceptually, using event-carried state transfer messages is an 
> asynchronous data replication mechanism. This approach makes the system 
> more fault tolerant, meaning that the consumers can continue functioning 
> even if the producer is not available. 
> It is also a way to improve the performance of components that have to process data 
> from multiple sources. 

### Domain event

> Domain event vs event notification
Domain events include all the information describing the event
Domain events can be useful even if no external consumer is interested in them. That’s especially true in event-sourced systems, where domain events are used to model all possible state transitions. 

> Domain event vs ECST
An ECST message provides sufficient information to hold a local cache of the producer’s data. 
No single domain event is supposed to expose such a rich model. 

# Designing Event-Driven Integration

The events in an EDA-based system are first-class design elements, affecting
both how the components are integrated and the components' boudaries themselves.

## Distributed Big Ball of Mud

A CRM publish a message.
The AdsOptimizaton bound context subcribes the CRM domain events.
The Reporting bound context also subcribes the CRM domain events.
The Reporting fetchs states from the AdsOptimizaton.
AdsOptimization and Reporting subcribe same events, and Reporting depends on the 
AdsOptimization's state, a delayed time is introduced in the Reporting bound context.
It process messages five minutes after receving them.

This is a terrible design. Let's analyze.

### Temporal Coupling

The AdsOptimization and Reporting bounded contexts are temporally coupled:
they depend on a strict order of execution.

To enforce the required execution order, the engineers intorduced the processing delay
in the Reporting system.
Obviously, this desn't prevent incorrect order of excuton:
- AdsOptimization may be overloaded and unable to finish the processing in 5 minutes.
- A network issues may delay the delivery of incoming messages to the AdsOptimization service
- The AdsOptimization can experience an outage and stop processing incoming messages.

### Functional Coupling

The Marketing and AdsOptimization bounded contexts both subcribed to the CRM's domain
events and endup implementing the same projection of the customer's data.

This's an example of functional coupling: multiple componets implementing the same business
functionality, and if it changes, both components have to change simultaneously.

### Implementation Coupling

If a new domain event is added to the CRM's model, it can potentially affect the project
models and thus, ignoring it will lead to project an inconsistent state.

## Refactoring The Event-Driven Integration

Exposing all the domain eents constituting the CRM's data model couples the subscribers to the
producer's implementation details.

The implemention coupling can be addressed by exposing either a much more restrained set of
evetns or a different type of events.

Don't expose events:
- CustomerCreated
- CustomerAddessedChanged
- CustomerPhoneChanged
- CustomerEmailChanged
- CustomerStatusChanged

Do expose events:
- CustomerProfileUpdated

Use Domain Event and Intergration Event 

Both implementation and functional couplign can be tackle by encapsulating the projection
logic in the producer: the CRM bounded contexts. Instead of exposing its implementaiton details,
the CRM can follow the consumer-drive contract pattern.

To tackle the **temporal coupling** between the AdsOptimization and Reporting bounded contexts,
the AdsOptimization component can publish an event notification message, triggering the 
Reporting component to fetch te data it needs.

# Event-Driven Design Heuristics

## Assume the worst

- The network is going to be slow
- Servers will fail at the most inconvenient moment
- Events will arrive out of order
- Events will be duplicated

Ensure that events are always delivered no matter what:
- Use the outbox pattern to publish messages reliably
- Ensure the subcribers will be able to deuplicate the messages and identify and reorder
out-of-order messages.
- leverage the saga and process manager patterns when orchestrating cross-bounded context.

## Use public and private events

Treat events as an inherent part of the bounded context's public interface.

### Evaluate consistency requirements

If the components can settle for eventually consisten data, use the ECST message.

If the consumer needs to read the latest write in the producer's
state, use an event notification message with a subsequent query
to fetch the producer's up-to-date state.

# Conclusion

Event notification
> A notification that something important has happened, but requiring the consumer to query the producer for additional information explicitly.

Event-carried state transfer
> A message-based data replication mechanism. Each event contains a snapshot of a state that can be used to maintain a local cache of the producer’s data.

Domain event
> A message describing an event in the producer’s business domain.
