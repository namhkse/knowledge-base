# Event-Driven Data Contracts

The format of the data to be communicated and the logic under which it is created form the data contract.

This contract is followed by both the producer and the consumer of the event data.

There are two components of a well-defined data contract:
- data definition
  What will be produced (i.e., the fields, types and data structures).
- triggering logic
  Why it is produced (i.e., the specific business logic that triggered the event's creation)

## Using Explicit Schemas as Contracts

The beast way to enforce data contracts and provide consistency is to define a schema for each event.

The producer defines an explicit schema detailing the data definition and the triggering logic.

The consumer can confidently build their microservice business logic against the schematized data.

> WARNING
> Any implementation of event-based communication between a producer and consumer that lacks an explicit predefined
> schema will end yp relying on an implicit schema.

A consumer must be able to extract the data necessary for its business processes, and it cannot do that without having a set of 
expectations about what data should be available.

> WARNING
> It may be tempting to build a common library that interprets any given event for all services,
> but this creates problems with multiple language formats, event eveolutions and independent release ccles.

Explicit schemas give security and scability to both consumers and producers.

## Schemas Definition Comments

Support for integrated comments and arbitrary metadata in the schema definition is essential for communicating the meaning of an event.

Schema comments help remove ambiguity about the data's meaning and reduce the change of misinterpretation by consummers.

There are two main areas where comments are valuable:
- Specifying the triggering logic of the event. Why an vent has been generated.
- Giving context and clarity about a particular field within the structured schema.
For example, a datatime field's comments could specify if the format is UTC, ISO, or Unix time.

## Full-Featured Schema Evolution

The schema format must support a full range of schema evolution rules.

Schema evolution enables producers to update output while allowing consumers to continue consuming the events.

Business changes may require that new fields be added, old fields be deprecated, or the scope of a field be expanded.

A schema evolution framework ensures that these chagnes can occur safely.

Without schema evolution support, producers and consumers are forced to coordinate closely.

An explicit set of schema evolution rules allow producers and consumers to updated in their own time. 

Forward compatibility
    New schema data can be read using the old schema
    OLD
    {
        "orderId": "123",
        "amount": 100
    }

    NEW
    {
        "orderId": "123",
        "amount": 100,
        "currency": "USD"
    }

Backward compatibility
    Old schema data can be read using the new schema.
    This enables a consumer of data to use a newer schema to read older data. 
    There are several scenarios:
    1. Consumers update data schema before producers
    2. Schema-encoded data is sent by a product deployed on customer hardware, such a cell phone.
    3. Consumer consumer may need to reprocess data in the event stream that was produced with an older schema version.

Full compatibility
    The strongest
    The uninon of forward and backward

## Breaking Schema Changes

While the producer can be easily changed, the impacts to downstream consumers vary and need to be taken into account.

> TIP
> The most important thing when dealing with breaking schema changes is to communicate early and clearly with downstream consumers.

# Designing Events

Best practices and anti-patterns.

## Tell the Truth, The Whole Truth, and Nothing but the truth

A good event definition is not a message indicating that something happend,
but rather the complete description of everything that happened during that event.

## Using a Singular Event Definition per Stream

An event stream shoudl contain events representing a single logical event.

## Use the Narrowest Data Types

Use the narrowest types for your event data.

Here are few avoidable real-world examples:
- Using string to store a numeric value.
- Using interger as boolean
- Using string as an enum

Enums are often avoided because producers fear creating a new enum token that isn't present in the consumer's schema.

## Keep Events Single-Purpose

One common anti-pattern is adding a type field to an event definition, where different type values indicating psecific subfeatures of the event.
