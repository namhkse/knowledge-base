# Chapter 5. Event-Driven Processing Basics

Event-driven microservices follow 3 steps:
1. Consume an event from an input event stream.
2. Process that event.
3. Produce any necessary output events.

Pseudo code
```
consumer
producer

while true:
    event = consumer.pollOne()

    outputEvent = process(event)

    producer.produce(outputEvent)

```

## Transformations

A transform processes a signle event and emit 0 or more output events.

Common transforms:
- Filter: emits 0 or 1 event
- Map: change key/value of the event. Emits exactly 1 event.
- MapValue: change only the value of the event. Emits exactly 1.
- Custom transform

## Branching and Merging Streams

A consumer application may need to **branch** event streams.

Topology = steps handle data input -> processing -> output

A scenario is emitting results to different output event streams.
For example, outputting events to a dead-letter stream in case of a processing error, instead of
droping them.

A consumer application may need to **merge** event streams.
Events from multiple input streams are merged then output ot a single output stream.

# Repartioning Event Streams

Event streams are partitioned according to the event key and the event partitioner logic.

Repartitioning is the act of producing a new event stream with one or more of the following properties:
- Different partition count: increase an event streams' partition count.

- Different event key: change key to ensure that events with the same key are routed to the same partition.

- Different event partitioner

## Example: Repartitioning an Event Stream

There is a stream of user data comming in from a web endpoint.

# Recovering from stateless processing instance failures

Recovering from stateless failures is the same as adding a new instance to a consumer gorup.

Stateless processors do not require any state restoration, which mans they can go back to 
processing events as son as they're assigned partitions.
