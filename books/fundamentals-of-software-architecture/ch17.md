# Microservices Architecture

Microservices is a popular architecture style in recent years.

# History

Microservices is heavily inspired by teh ideas in domain-driven design (DDD).

Bounded context inspired microservies.

When a developer defines a domain, that domain includes many entities and behaviors, indetified in artifacts such as code and database.

For example domain CatalogCheckout which includes:
- catalog items
- customers
- payment

Within a bounded context, the internal parts, such as code and data schemas, are coupled together to produce work;
but they are never coupted to anything outside the bounded context, such as a database, or classes from another bounded context.

When an architect design an system that favors reuse, they also favor coupling to achive that reuse, either by
inheritance or composition.

If the architect's goal requires high degrees of decoupling, then they favor duplication over reuse.

# Topology (how they are organized and conneced to each other)

The service size in microservices is small.

# Distributed

Each service runs in:
- its own process
- physical computer or virutal machine, or container.

Performance is often the negative side effect of the distributed nature of microservices.

Network calls take much longer than method calls.

# Bounded Context

Each service models a domain or workflow.

In monothic, developers share common classes
In micorservies, developers try to avoid couplign and prefer duplication to coupling.

## Granularity

An often mistake is services are too small, which requires them to build communication links back between the servces to do work.

Teh purpose of service boundaries in microserves is to capture a domain or workflow.

Guidelines help find the appropriate boundaries:
- Purpose: each microserve shoudl be cohesive, contribuign one significant behavior on behalf of the overall application.
- Transactions: transactions cause issues in distributed architectures, avoid them to get better designs.
- Choreography: a set of services that offer excellent domain isolation require extensive communication to function, consider bunding these services
                back into a larger service to avoid the communication overhead.

# Operation Reuse

Once a team has built serveral microservcies, they relize that each ahs common elements.

The sidecar pattern offers a solution to this problem.
The side component ahndles all the operational concerns that teams benefit from coupling together.

Each sidecar wires into the service plane, which forms the consistent interface to each service.

Architects use service discovery.

# Communication

Architects must decide
- sync communication (the caller waits the callee)
- async communication (events, messages)

## Choreography and Orchestration.

Choreography utilizes the same communication as a broker event-driven architecture.
No central coordiantor exists.

Each service calls other services without a central mediator.
If an architect needs to coordinate across several services they can create their own localized mediator.
For example, the `ReportCusotmerInformation` mediator calls `CustomerWishlist` and `CustomerDemographics` services.

Choreography's trade-off are error handling, coordination for complext business processes.

## Transaction and Sagas 

Transaction coordination accross services.

Because the decoupling in the architecture encourages the same level for databases.

> The best advice: Don't do transactions in microservies - fix the granularity components instead.

A popular distrubted transactin pattern is the **saga pattern**.

A service acts a mediator accross multiple service calls and coordinates the transaction. The mediator calls each part of the transaction, records success
or failure, and coordinates result. If everythign goes as planed, databases update synchronously.
